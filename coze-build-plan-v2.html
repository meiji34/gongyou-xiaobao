零、变更摘要

根据你的反馈，计划有以下三项关键变更：

变更一：客户端改为安卓端

原方案：发布为 Coze Web 链接，评委浏览器体验

新方案：开发安卓端客户端，基于你提供的 index.html 原型（4 屏交互：首页/权益咨询/暖心树洞/便民工具）封装为安卓应用

  • 原型已有完整的 UI 设计：语音入口卡片、气泡对话、法条引用卡片、转接卡片、心情选择器、底部语音输入栏
  • 技术路线建议：WebView 封装（最快，直接嵌入你的 HTML）→ 后续可升级 React Native / Flutter
  • 语音能力：调用安卓系统麦克风做 ASR 录音，通过 Coze API 传入
  • 与 Coze 后端通信：HTTP 调用 Coze 的 chat completion API

变更二：P2 知识库 → 法律 Skill 替代

原方案：自建 RAG 知识库（收集劳动法 PDF → 分段 → 向量化 → 检索）

新方案：使用 WorkBuddy 推荐市场的法律 Skill 替代，免去数据收集/分段/向量化全部工作

已搜索到两个高度匹配的候选 Skill：

Skill核心能力适配度推荐
fadada-laws-and-regulations-retrieval
法大大法规检索		 检索中国大陆法律法规、行政法规、地方性法规、司法解释及条文内容。支持"查法条""找法规""这条法律怎么说"等自然语言触发 极高 首选
fazhi-law
法治法律专家		 调用 2 亿+权威法律数据，融入资深律师执业心得，覆盖民商事、刑事、行政、执行等全部法律事由 极高 推荐组合

建议组合使用：fadada 负责条文级精确检索（"《保障农民工工资支付条例》第三十条"），fazhi-law 负责整体法律推理和通俗化解释。两者可覆盖你方案中劳动法/工伤/工资拖欠/社保/加班结算的全部需求。

核心优势：无需自建知识库 → P2 阶段从"收集+分段+向量化"简化为"安装+配置 Skill"，节省大量时间，且数据权威性更高（2 亿+权威数据 vs 自己收集的 PDF）。

变更三：长期记忆采用 shujuku 方案

原方案：Coze Memory 变量 + Database 简单建表

新方案：参考 AlbusKen/shujuku 仓库的"神·数据库"方案，引入结构化长期记忆体系

shujuku 仓库提供了完整的长期记忆管理架构，我们提取可落地的核心机制：

shujuku 机制在工友智能体中的应用
聊天持久化
表格数据写入聊天历史，自动恢复		 工友的档案信息（工种/入职日期/历史咨询摘要）持久化到对话历史，重启不丢失
SQL 查询 API
SQLite 模式下的只读 SQL 查询		 支持"这个工友上次问过什么""有多少人反映过食堂问题"等结构化查询
世界书注入
结构化数据注入 AI 上下文		 工友档案自动注入对话上下文，AI 能"记住"工友背景（如"你是钢筋工，入职 3 个月"）
callAI 受限代理
安全调用 AI 做摘要/分析		 每轮对话结束后，自动摘要写入工友档案表
getStoryContext
提取对话上下文		 多轮追问时获取前 N 轮上下文，支持"先说欠薪再补充三个月"的连续对话
数据隔离
按聊天+标识分槽存储		 不同工友的档案隔离，不会串数据
适配说明 shujuku 原为 SillyTavern 生态设计，我们的 Coze 环境不会直接使用其插件。但我们会借鉴其架构理念，在 Coze 的 Database + Memory + Workflow 中实现等效的长期记忆机制。核心是：结构化存储 → 上下文注入 → 多轮记忆 → 自动摘要写入。

P1

编写工友管家人设、通俗化翻译指令、安全边界规则。无变更。

P5（变更）：shujuku 理念长期记忆

  • 自动摘要写入（对应 shujuku callAI）：每轮对话结束后，用 LLM 摘要写入档案表
  • 多轮记忆（对应 shujuku getStoryContext）：获取前 N 轮上下文，支持连续追问

二、安卓客户端方案详解

你的 index.html 原型已经是一个完整的 4 屏交互设计，直接封装为安卓应用是最快路径。

2.1 技术路线对比

方案开发周期优点缺点推荐
WebView 封装 1-2 天 直接复用你的 HTML 原型，零重构 性能略低于原生 首选（MVP）
React Native 5-7 天 接近原生性能，可扩展 需重写 UI 组件 后续升级
Flutter 5-7 天 高性能，跨平台 需重写 UI，Dart 学习成本 后续升级
原生 Kotlin/Java 7-10 天 最佳性能和系统集成 开发周期最长 不推荐 MVP
推荐：WebView 封装 你的 HTML 原型已有完整的状态管理（navigateTo/toggleRecording/selectMood）、4 屏切换、语音按钮动画。用安卓 WebView 封装只需：(1) 创建安卓工程 (2) 放入 HTML 到 assets (3) 配置 WebView (4) 添加麦克风权限 (5) 对接 Coze API。这是截止日期前最快落地的方式。

2.2 原型 4 屏与 Coze 后端的对接

原型页面UI 元素对接 Coze 后端
首页 语音入口卡片（按住说话）、4 个快捷入口、底部 Tab 语音 → Coze ASR → 意图路由 → 跳转对应页
权益咨询页 用户气泡 + AI 气泡 + 法条引用卡片 + 转接卡片 + 底部语音栏 文字 → Coze chat API → 法律 Skill 检索 → 返回含法条卡片
暖心树洞页 心情选择器 + 用户气泡 + AI 暖心回复 + 底部语音栏 文字 → Coze chat API → 心理陪伴工作流 → 暖心回复
便民工具页 报修/食堂/班车/安全微课卡片 + 班车信息卡片 点击 → Coze 对应 Workflow → 返回结果卡片

2.3 安卓端核心功能实现

语音输入实现

  1. 安卓端录音：MediaRecorder 录制音频文件
  2. 上传 Coze：通过 multipart/form-data 上传到 Coze ASR 接口
  3. 获取文字：ASR 返回识别文本
  4. 发送对话：文本传入 Coze chat completion API
  5. 语音播报：Coze TTS 返回音频 → MediaPlayer 播放

图片上传实现

  1. 安卓端拍照/选图：调用系统相机或相册
  2. 上传 Coze：multipart 上传图片
  3. OCR 识别：Coze 多模态插件识别工资条/合同
  4. 结果传入对话：识别文本进入对话流

三、法律 Skill 能否替代 P2 自建 RAG？

结论：可以，且强烈推荐替代。

对比维度自建 RAG 知识库（旧 P2）法律 Skill（新 P2）
数据覆盖 仅限自己收集的 PDF（可能遗漏 2 亿+权威法律数据，覆盖全部法律事由
条文检索 向量检索，可能有偏差 条文级精确检索，支持自然语言查询
数据权威性 取决于收集来源 权威法律数据库，官方来源
搭建时间 2-3 天（收集+分段+向量化+调试） 半天（安装+配置调用节点）
维护成本 法规更新需手动同步 Skill 维护方更新，自动同步
幻觉风险 中（检索不到时可能编造） 低（权威数据 + 标注引用来源）
通俗化翻译 需自己在 Prompt 中实现 fazhi-law 内含"资深律师执业心得"，可通俗化
比赛呈现 "自建知识库"是一个技术亮点 "整合专业法律 Skill"是工具整合能力体现
比赛策略提示 方案文档中提到评审看重"工具整合"能力。使用法律 Skill 恰恰展示了你整合专业工具的能力——这比自建一个覆盖不全的 RAG 库更能体现"AI 协同"思维。在文档中可以这么写："本方案未重复造轮子，而是整合 fadada 法规检索和 fazhi-law 两个专业法律 Skill，实现 2 亿+权威法律数据的即时接入，体现了人机协同中的工具整合能力。"
唯一注意点 法律 Skill 是 WorkBuddy 平台的 Skill。如果最终需要在 Coze 平台上运行，需要确认：(1) Coze 是否支持调用外部 Skill，或 (2) 是否需要在 Coze 中配置等效的插件（Plugin）。如果 Coze 不支持直接调用 WorkBuddy Skill，我们有两个备选方案：A. 在 Coze 插件市场找等效法律插件；B. 用 Coze 自定义插件封装 Skill 的 API 调用。这一点需要在 P0 阶段验证。

4.3 记忆流转流程（借鉴 shujuku 完整链路）

  1. 对话开始：从 Database 查询工友档案 → 注入 Prompt 上下文（对应 shujuku 世界书注入）
  2. 对话进行：Memory 变量保留当前会话 N 轮历史（对应 shujuku getStoryContext）
  3. 对话结束：Workflow 末尾 LLM 节点生成本轮摘要（对应 shujuku callAI）
  4. 持久化：摘要写入工友档案表 + 工单记录写入工单表（对应 shujuku 聊天持久化）
  5. 下次对话：恢复档案 → 注入 → AI"记得"工友是谁、上次问了什么
